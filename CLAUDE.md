# Project guide for AI-assisted development

Enterprise accounting platform (modular monolith). Read `docs/architecture.md`,
`docs/accounting-engine.md` and `docs/accounting/*.md` before changing anything financial.

## Non-negotiables

- The general ledger is the source of truth; never maintain independent totals.
- Money: PostgreSQL `NUMERIC(19,4)`, decimal strings over the API, no JS floats.
- Posted journals are immutable; corrections are reversal/adjusting entries.
- All financial mutations run in one PostgreSQL transaction and write an audit row via `AuditService.record(entry, tx)`.
- Authorization is enforced only in NestJS (`@RequirePermissions(P['x.y'])`); UI checks are cosmetic.
- No hard-coded account ids, tax rates or role names in business logic.
- AI features (Phase 9) are advisory only and never post transactions: `modules/ai` creates drafts through `BillsService` / `ExpenseClaimsService`, answers only from report services, and stores flags/suggestions beside the books. Keep `ai.logic.ts` pure; `AI_PROVIDER=HEURISTIC` must keep working offline (tests rely on it).

## Workflow

- Every ledger write goes through `AccountingPostingService.postEvent/postEntry` (reversals through `reverseEntry`); resolve accounts via `AccountsService.resolveMapped` or `PostingRulesService.resolve`, never by id. The gateway also enforces dimension rules (`DimensionRulesService`) and account branch applicability; keep `dimension-rules.logic.ts`, `posting-rules.logic.ts`, `fx-lines.logic.ts`, `recurring.logic.ts`, `prepayments.logic.ts` and `reporting/cash-flow.logic.ts` pure. Pass the real `actor` and the module's posting `permission` (`{ permission: P['bill.post'] }`); the gateway validates authority, branches, dimensions, source document and period state (`OPEN / SOFT_CLOSED / CLOSED / LOCKED`). Draft-time period checks use `resolvePeriod(..., { draft: true })`. Give every distinct posting event its own source identity - never reuse a parent id for repeated events (see the realized-FX fix).
- Accruals set `autoReverseDate`: the engine posts the mirror REVERSAL in the same transaction. Recurring journals (`recurring_journal_runs`) and prepayment instalments (`prepayment_schedules`) are the source identity of the journals they generate; AUTO_POST templates and prepayment activation / recognition are posting decisions (`journal.post` / `prepayment.post`). Opening balances are OPENING drafts offset to `OPENING_BALANCE_EQUITY`.
- Subledger documents keep business status (DRAFT/APPROVED/PARTIALLY_PAID/PAID/VOID) separate from accounting status (UNPOSTED/POSTED/REVERSED); void = reversal journal, never an edit. Allocations never create journal entries.
- Orders (quotation / sales order / purchase request / purchase order) share one `orders` table and `OrdersService`; they never post. Fulfilment counters change only via `OrderFulfillmentService` inside the fulfilling document's transaction.
- Stock only moves through `InventoryService.receive/issue` (movements + FIFO layers + balances); the document that moves it posts the returned cost in the same transaction via `DocumentStockService`. Valuation in `modules/inventory/valuation.ts` is pure - keep it that way.
- Fixed asset cost / accumulated depreciation change only inside `FixedAssetsService` / `DepreciationRunsService` transactions that post the journal; depreciation arithmetic (`modules/fixed-assets/depreciation.ts`) and statement matching (`modules/banking/matching.logic.ts`) are pure - keep them that way. Bank balances are the GL account's balance, never stored.
- Tax is data: never hard-code rates or tax accounts. Documents call `TaxEngineService.applyToLines` when lines change and `postingLines` + `record` when posting (`reverse` on void); tax arithmetic in `modules/tax/tax.logic.ts` stays pure. Dimension references on any line go through `DimensionsService.validateRefs` inside the writing transaction. Budgets never post; variance reads posted journal lines.
- Journal lines are always in the company base currency. Foreign amounts stay on the document; resolve rates only via `ExchangeRatesService.rateFor/documentRate` and convert with `Money.convert`; realized/unrealized FX entries come from `FxService`. Currency schemas that may be omitted use `optionalCurrencyCodeSchema` (`currencyCodeSchema` defaults to PHP).
- Approval gating: documents that can be workflow-gated call `ApprovalsService.open` on submit and `assertApproved` before approve/post; never bypass it per document type.
- Subledger "expected" balances come only from `SubledgerBalancesService.compute` (reconciliation records and the integrity checker share it); never re-derive them elsewhere. Reconciliation approval is four-eyes and blocked by open exceptions / unexplained variance above `accounting_policies.reconciliation_materiality`.
- Attachments are metadata + files under `STORAGE_DIR` via `AttachmentsService`; they never influence posting.
- Integrations (`modules/integrations`, docs in `docs/integrations/`) are adapters: connectors return external records, importers validate with the API's Zod schemas and call the domain services (`CustomersService`, `InvoicesService`, `CustomerPaymentsService`, `StatementsService`); nothing in the platform writes journal rows. Posting needs an explicit `:post` scope. Provider credentials go through `CredentialsService` (encrypted) and are never returned or logged; mapping / retry / signature / health logic stays pure. New provider = one connector class + `connectors/index.ts`.
- Domain events for webhooks are written with `OutboxService.enqueue(tx, ...)` inside the business transaction (global module); never emit outbound webhooks directly.
- Ledger reads that need one account (control, bank GL, mapped account) pass `accountIds` to `GeneralLedgerService.activity` so the (company, account) index is used; only statements aggregate the whole ledger, and trends use `activityByMonth` (one read). Integrity checks are single capped queries - never stream every posted line into Node; dashboards show the latest stored `integrity_runs` row (`GET /integrity/runs/latest`), not a live audit (`docs/performance.md`).
- Authority is never widened by a less-privileged actor: role assignment requires the assigner to hold `role.assign` in the granted scope (`RoleAssignmentService.assignWithin` takes the actor), integration and API-key scopes are capped by the grantor's own permissions (`grantableScopes`), and CSV exports neutralise formula-leading cells (`csv.ts`). State-changing public routes (sign-in) accept only script-initiated requests (JSON / `X-Requested-With` / Bearer) - `CsrfGuard`.
- Authorization context is cached per user for a short TTL (`AuthorizationCacheService`, global): any write that changes what a user may do (role assignment, role permissions, delegations, user / company status) must call `invalidateUser` / `invalidateAll`; session validity is never cached.
- Delegated authority (`modules/delegations`): approval-type permissions only (`DELEGABLE_PERMISSIONS`). Every approve-type service calls `AuthorityService.assert(tx, actor, permission, doc)` after loading the document; the guard accepts a delegated permission, the service enforces scope / amount / SoD and records usage. Never treat a delegation as a role.
- Financial close (`modules/financial-close`) is the only UI path that closes a period: automatic checklist tasks are evaluated from ledger data and never ticked by hand; policy flags in `accounting_policies` decide which failures block. Completion calls `FiscalPeriodsService` inside the same transaction.
- Enterprise controls (H5): document-level SoD goes through `SodService.checkActorSeparation` with the document ref (WARN is audited); workflow gating with `assertApproved` opens the request on its own connection because the caller rolls back; `UPDATE` audit events with `previousValue` + `newValue` objects produce `field_changes` rows automatically (pass `metadata.reason`); suspense figures come only from `SuspenseService.monitor`; the control dashboard (`modules/controls`) composes other services and stores nothing.
- Data infrastructure (H6): document numbers come only from `DocumentNumberingService.allocate(companyId, type, year, tx, { branchId })` inside the document's transaction (rules in `numbering_rules`, never renumber issued documents); CSV imports (`modules/data-infrastructure`) validate on upload and commit only through the owning domain services - financial datasets all-or-nothing, master data row by row; exports read through the report services and are audited; opening balances offset to `OPENING_BALANCE_EQUITY` (AR / AP items, `OPENING` stock adjustments, `FixedAssetsService.openingBalance`) and are proven by `GET /opening-balances/report`.
- Reporting engine (H7): report definitions are JSON layouts (`packages/validation/src/reporting-engine.ts`) run by `ReportEngineService`, which reads figures only through `GeneralLedgerService.activity` and approved `budget_lines` - never store report figures; keep `report-engine.logic.ts` (windows, selectors, sign presentation, formulas, variances) pure; system layouts in `system-reports.ts` are seeded per company and read-only (copy to customise). Traceability (`TraceService`) and the journal control summary compose existing tables and never re-derive ledger totals; `trace.view` is a restricted view like `audit.view`.
- Operations (H8): every scheduled job registers with `JobRegistryService` (`scheduleRepeatable` for jobs that own their schedule, `JobRunnerService.schedule(queue, name, repeat, data, description)` on the integration runner) and runs through `execute` - advisory lock per job name + `job_runs` row - never register a bare BullMQ worker that filters `job.name` (one queue = one dispatching worker). Jobs must stay idempotent; return a small summary object, not figures. BullMQ keys carry `QUEUE_PREFIX`; a checkout sharing Redis needs its own prefix. Readiness = `/health/ready` (schema current + not draining); operations endpoints are organization-level and `operations.view` is restricted like `audit.view`.
- Receivables and payables screens are one config-driven implementation (`apps/web/lib/subledger/config.ts`, `components/subledger/*`); fix bugs once, not per side. AR-only behaviour (credit, deliveries, collections, disputes, write-offs, refunds, dashboard) lives in `components/receivables/*` and is injected where `cfg.side === 'AR'`.
- AR platform (`modules/receivables`, docs in `docs/accounts-receivable/`): credit policy is data (`credit_rules`, `ar_settings`, `dunning_policies`, `payment_terms`) evaluated by `CreditService.check` at sales-order / invoice submit and approve; a credit hold always blocks. Balances leave the subledger only through posted write-offs (`WriteOffsService`, allocation source `write_off_id`); refunds only through approved refund requests that create + post a REFUND receipt; deliveries issue stock and post COGS, and an invoice with `deliveryId` never moves stock again. `ArReportsService.reconciliation` (used by `SubledgerBalancesService`) must subtract write-offs - keep the two in step when adding AR-side postings.
- AP platform (`modules/payables`, docs in `docs/accounts-payable/`): vendor state gates documents (`VendorsService.assertUsable` for purchase orders, bills and payments; a hold or block always blocks). Early-payment discounts are allocation rows (`vendor_payment_allocations.discount_payment_id`, third source) posted to `PURCHASE_DISCOUNT` by the payment; payment holds (`bill_holds` + `vendor_bills.on_hold`) never touch the ledger and are enforced in `BillsService.lockTargets`. Payment runs only select bills - execution goes through `VendorPaymentsService.createInTx/postInTx({ approvedUpstream: true })` per vendor. AP accruals post Dr expense / Cr `ACCRUED_EXPENSE` plus the reversal in one transaction and never touch the AP control. Goods bills without a product line must not post to the inventory account (the stock subledger owns it). AP-only UI lives in `components/payables/*` and is injected where `cfg.side === 'AP'`.
- Consolidation (`modules/consolidation`, docs in `docs/consolidation/`): member ledgers are read, never written - a run keeps everything the group adds in `consolidation_adjustments` by account code, generated by data-driven `elimination_rules` (regenerated on every prepare) plus manual entries; runs are fiscal-year-to-date; finalizing freezes a `snapshot` of member figures (four-eyes, readiness-gated) and `FINALIZED_RUN_DRIFT` reports later entity postings. Keep `consolidation.logic.ts` pure (translation with CTA plug, eliminations, NCI, equity pickup, `consolidate`). The NCI share of current-year profit is a presentation allocation, not a journal. Intercompany settlement posts both bank legs in one transaction (`INTERCOMPANY_SETTLEMENT`); intercompany numbers are per originating company.
- Revenue recognition (`modules/revenue`, docs in `docs/revenue-recognition/`): policy is data (`revenue_policies`, `revenue_settings`; line -> product -> company default). Invoice posting calls `RevenueSchedulesService.deferInvoiceLines` inside its own transaction - deferred lines credit `DEFERRED_REVENUE` and get a `revenue_schedules` row (lines are the source of truth, base currency, dimensions carried); draft-time `validateDraftLines` refuses bad windows / milestone splits. Deferred revenue leaves the balance sheet only through recognition runs (`RevenueRunsService.create`: one ADJUSTING journal per run, source `REVENUE_RECOGNITION_RUN`, permission `revenue.recognize`; reverse latest first); milestones fall due only when completed; a void is refused while any line is recognized (`REVENUE_RECOGNIZED`). Keep `revenue.logic.ts` pure. Reports and the `REVENUE_RECOGNITION` close check derive from schedule lines and are proven against the ledger (`DEFERRED_REVENUE_VS_LEDGER`).
- Bank feed (`modules/bank-feed`, docs in `docs/bank-feed/`): rules and settings are data (`bank_matching_rules`, `bank_feed_settings`); keep `bank-feed.logic.ts` pure (rule / document / history suggestions). The feed never writes journals and never matches without a document: applying a suggestion or explaining a line posts through `BankingService.createTransactionInTx/postTransactionInTx`, `CustomerPaymentsService` or `VendorPaymentsService` inside one transaction and then matches the statement line (`bank_line_matches.kind = RULE`); `IGNORE` marks the line DUPLICATE. Auto-apply needs an actor (import / refresh) - the daily sweep only suggests. History is derived from matched lines, never stored.
- Payroll (`modules/payroll`, docs in `docs/payroll/`): employees and pay items are data (rates, brackets, caps and accounts live in `pay_items` / `payroll_settings`, falling back to the `SALARY_EXPENSE` / `EMPLOYER_CONTRIBUTION_EXPENSE` / `STATUTORY_CONTRIBUTIONS_PAYABLE` / `WITHHOLDING_TAX_PAYABLE` / `EMPLOYEE_PAYABLE` mappings); keep `payroll.logic.ts` pure. A pay run is the only path from salaries to the ledger: `calculate` builds payslips (the subledger of `EMPLOYEE_PAYABLE`, together with posted expense claims), approval is four-eyes (`payroll.approve`, delegable, SoD vs `payroll.manage`, workflow doc type `PAY_RUN`), `post` writes one journal on the period end (`PAY_RUN`), `pay` settles the payable from a bank account (`PAY_RUN_PAYMENT`) and marks reimbursed claims PAID only through `ExpenseClaimsService.settleThroughPayroll`; only unpaid runs reverse. `employee.view` / `payroll.view` are restricted views.
- Leases (`modules/leases`, docs in `docs/leases/`): contracts and `lease_settings` are data; keep `lease.logic.ts` pure (present value, schedule with the rounding plug, classification, maturity). Carrying figures on `leases` change only inside transactions that post through the gateway: `commence` (`LEASE_COMMENCEMENT`), lease runs (`LEASE_RUN`, one ADJUSTING journal per run, reversed latest first), `pay` (`LEASE_PAYMENT`, source identity = the schedule line, schedule order, in arrears only after the run), `remeasure` (`LEASE_REMEASUREMENT`, source identity = the event) and `terminate` (`LEASE_TERMINATION`, gain / loss on `GAIN_LOSS_ON_DISPOSAL`). Accounts resolve lease override -> `RIGHT_OF_USE_ASSET` / `ROU_ACCUMULATED_DEPRECIATION` / `LEASE_LIABILITY` / `LEASE_INTEREST_EXPENSE` / `LEASE_EXPENSE` mappings. Exempt leases never touch the balance sheet. `lease_events` carry the signed effects the integrity checks and the register rollforward replay - write one for every carrying change. Asset splits (`FixedAssetsService.split`) are register-only and never post.
- Treasury (`modules/treasury`, docs in `docs/treasury/`): cash is only ever the GL - `CashPositionService` reads bank GL balances, never stored totals. Inter-account transfers post two legs through `CASH_IN_TRANSIT` (`BANK_TRANSFER_OUT` on send, `BANK_TRANSFER_IN` on settle, realized FX via `FxService`); the in-transit balance must equal open transfers (integrity). Payment files package already-posted vendor payments and never post; petty cash funds own a dedicated cash account, vouchers post Dr expense / Cr fund, replenishment is a `BankingService` withdrawal, so `fund GL = imprest - unreimbursed vouchers`. Forecast flows, planned items and snapshots never post; keep `treasury.logic.ts` pure. Policy (`treasury_settings`, `bank_account_profiles`) is data.
- UI: one design system (`docs/design-system/`). Tokens live only in `packages/ui/src/styles.css` (+ `packages/ui/src/theme`); modules use semantic utilities (`text-positive`, `bg-card`, `duration-fast`, `type-label`), never raw colours or durations. Status = `StatusBadge` / `components/status` (icon + text, never colour alone); money = `Amount` / `CurrencyDisplay`; posting & approving = `OperationDialog`; lifecycles = `StepTimeline`; loading/empty/error = shared skeletons, `EmptyState`, `ErrorState`. Motion is CSS + `@accounting/ui` helpers (no animation library) and must honour reduced motion.
- Shared packages `types`, `validation`, `config`, `money` are compiled: after editing run `pnpm build:packages` (or keep `pnpm dev` running).
- Schema change: edit `apps/api/src/database/schema/*.ts` -> `pnpm db:generate` -> review SQL -> `pnpm db:migrate`.
- New permission: add to `packages/types/src/permissions.ts` (+ system roles) -> build -> `pnpm db:seed`.
- e2e suites DROP the schema: they only run against a database whose name contains `test` (see `apps/api/test/setup-env.ts`); unit Jest is scoped to `src/`. Each git worktree gets its own test database automatically (`accounting_test_<worktree>`, created by `test/global-setup.ts`); set `TEST_DATABASE_SUFFIX` to isolate another checkout or session - never run two e2e suites against one database.
- Tests: `pnpm test` (unit), `pnpm --filter @accounting/api test:e2e` (needs Docker infra), `pnpm --filter @accounting/web test:e2e` (needs running stack).
- Playwright specs import `test` / `expect` from `e2e/fixtures.ts` (never from `@playwright/test` directly) and start sessions with `login(page)` from `e2e/helpers.ts`: the fixture writes the context's cookies back to `e2e/.auth/admin.json` after every admin test so the API's refresh-token rotation never trips its reuse detector, and `login()` waits for the shell or the login form (`settle`) and re-logs in when the stored session is gone. Never sign the shared admin session out through the UI; switch users only via `login(page, FINANCE)`.
- Lint/typecheck before finishing: `pnpm lint && pnpm typecheck`.

## Conventions

- Errors: throw `AppError` subclasses with codes from `error-codes.ts`; never leak raw DB errors.
- Controllers stay thin; services own transactions and business rules.
- Zod schemas live in `@accounting/validation` and are reused by web forms (`useForm<z.input<S>, unknown, z.output<S>>`).
- Docker PostgreSQL is published on host port 5433 (5432 is often taken locally).
